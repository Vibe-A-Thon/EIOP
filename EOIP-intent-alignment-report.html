Is EOIP being built into what it was meant to be?

EOIP is meant to become an organization's living brain: it connects to every work system, keeps one constantly updated knowledge graph, and lets anyone ask any question and get an answer backed by evidence. This report compares that intention with what the code does today, explains where and why it has drifted, and sets out the plan to bring it back on track.

What EOIP is meant to be

The owner's intention in plain language. The full analysis breaks it into 26 testable statements; these are the eight ideas behind them.

1

Runs at the client

Self-hosted, central or distributed, as one app or (preferred) a suite of apps that can also be used individually.

2

Local-first, not local-only

Works without the cloud; the client decides whether to connect cloud services, and EOIP provides the connections.

3

Any proven database

HugeGraph, Neo4j, Neptune, other graph databases or NoSQL, queried through EOIP's own query language.

4

Connects to everything

An adapter framework for Jira, Confluence, ServiceNow, GitHub/GitLab and more, pulling data in many ways.

5

A living brain

Knowledge, code and meta graphs combined into one organizational brain, updated continuously, with history never destroyed.

6

Anyone asks anything

Every role can ask factual, reasoning or "meaning" questions, and gets evidence, a confidence score and related answers.

7

Secure AI from day 0

A local model is the default and improves over time, but the core still works with the model off or no vector database.

8

Best in its category

Features come from ongoing research of competitors; their weaknesses become EOIP strengths, built in-house.

What should shrink so that the product gets deeper instead of wider. Nothing is deleted while a route, test or registry entry still refers to it.

Seven decisions only the owner can make

The coding agent must ask about these, not assume an answer.

  1. Which NoSQL database comes firstMongoDB (its SSPL licence may conflict with redistribution), Apache Cassandra, ScyllaDB, or another Apache-2.0 store. AGPL is ruled out.
  2. The default local AI model and acceptable licencesWhich model to use for each hardware tier, and whether only Apache-2.0/MIT licences are allowed or community licences with usage clauses too.
  3. External AI model policyWhich kinds of data may ever leave the organization, to which providers, and whether the external option ships at all.
  4. Who triages the requirementsWho signs off keep or drop for the 2,603 records, and whether whole programmes (for example Moonshots, or the advanced Graph Neurons tiers) are deferred.
  5. Suite release orderKeep the suite plan's first wave, or put the Ask-first home and role workspaces first (as this analysis recommends).
  6. Permissions when a source's access rules are unknownDeny by default (recommended) or allow within the tenant.
  7. Distributed topology priorityOne central brain first, or a hub-and-spoke federation of departmental brains early.

Glossary

Terms used in this report.

Knowledge graph
Things (requirements, code, people, services) stored as points, with the relationships between them stored as links.
Evidence / provenance
The record of where a link came from: which system, which document or commit, when, and how sure we are.
Living brain
A knowledge graph kept current automatically as the connected systems change.
Connector / adapter
The code that reads data from another system, such as Jira or GitHub.
Incremental sync
Fetching only what changed since the last sync, instead of re-reading everything.
Query language
A precise way to ask the graph a question. EOIP should have one of its own that works on any supported database.
Pushdown
Translating a query into the database's native language so the database does the work, instead of EOIP fetching item by item.
Simulation
Output generated to look like a real result when the real capability (for example a model) is not available.
Confidence (calibrated)
A score that matches reality: answers marked 80% confident should be right about 80% of the time.
ACL
Access control list: who is allowed to see an item in its source system.
Crypto-shredding
Erasing personal data by destroying its encryption key, so history and structure survive but the data can no longer be read.
Work package (WP)
A unit of corrective work with a goal, scope and executed acceptance test.
