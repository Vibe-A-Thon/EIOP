# GitHub Organization Setup

## Prerequisites and Decisions

Use the user-confirmed organization [AvyukthiAI](https://github.com/AvyukthiAI). Verify the signed-in account's administrator/repository-creation permissions, recovery access, organization visibility policies, billing authority and available private-repository controls. The public organization page does not establish private membership or administrator access, and no particular paid plan is assumed.

New product repositories default to **private**. Keep first-party proprietary terms and existing third-party notices; do not select GitHub's Apache/MIT license template. No repository creation commands in this document were executed by the documentation task.

## Access Model

Proposed teams: `suite-maintainers`, `platform-maintainers`, `ui-maintainers`, `security-reviewers`, `release-managers`. Start with the actual people available; one person can belong to several teams. Use minimal base permissions and grant repository access deliberately. Avoid a broadly privileged parent team that unintentionally gives all child teams access to the operator plane. GitHub teams support repository access management and nested inheritance. [Official team documentation](https://docs.github.com/en/organizations/organizing-members-into-teams/about-teams).

For each repository configure:

1. Default branch `main`; pull requests for changes; no force push or branch deletion on protected release branches.
2. Required checks that actually exist and are stable; protected release tags and an explicit emergency bypass policy.
3. CODEOWNERS with valid organization members/teams that have appropriate repository access; required review where supported.
4. Actions allowlist, workflow permission minimums, protected release environments, bounded artifact retention and spending alerts.
5. Secret reporting/rotation process and secret scanning controls available to the selected plan.
6. Private package read access for authorized consuming repositories; repository access alone does not universally grant package access.

Ruleset availability varies with visibility and plan. Verify actual enforcement with an intentionally denied push or test PR; a configuration screenshot is insufficient. [GitHub rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets). CODEOWNERS requests/restricts reviews only in conjunction with the appropriate branch policies; it is not an access-control substitute. [GitHub code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners).

## Create the Pilot Repositories

Authenticate interactively through GitHub CLI; do not paste tokens into source or this handbook. Check the signed-in account and organization before running creation. The commands below create remote private repositories, so they are an implementation action, not a read-only check.

```powershell
gh auth login --hostname github.com --git-protocol https --web
gh auth status
```

Run the following reviewed PowerShell block once, after confirming creation authority. It deliberately fails on an empty/invalid organization handle or an unexpected GitHub error. If repositories already exist, inspect them and remove them from this creation list; do not delete or reinitialize them to make this command succeed.

```powershell
$Org = 'AvyukthiAI'
if ([string]::IsNullOrWhiteSpace($Org) -or $Org -notmatch '^[A-Za-z0-9][A-Za-z0-9-]*$') {
    throw 'Set a valid GitHub organization handle.'
}
gh api "orgs/$Org" --jq .login
if ($LASTEXITCODE -ne 0) { throw 'Organization lookup failed; do not create repositories.' }
$Pilot = @(
    'eoip-suite',
    'eoip-engineering',
    'eoip-contracts',
    'eoip-ui',
    'eoip-suite-home',
    'eoip-query-portal',
    'eoip-knowledge-portal'
)
foreach ($Name in $Pilot) {
    gh repo create "$Org/$Name" --private --description "EOIP suite component: $Name"
    if ($LASTEXITCODE -ne 0) { throw "Creation failed for $Name. Inspect remote state before retrying." }
}
```

This creates **empty** repositories, without an open-source license or autogenerated commit. That makes provenance-preserving initial import possible without overwriting a generated history. Set `main` after the first reviewed push if needed. `gh repo create` supports organization-qualified names and explicit visibility. [GitHub CLI reference](https://cli.github.com/manual/gh_repo_create).

The seven repositories above are the starting set, not the entire pilot dependency closure. Create `eoip-sdk` for the shared client work in MULTI-004, `eoip-suite-gateway` before MULTI-005 and `eoip-verification` when the early MULTI-013 harness starts. Create runtime/package repositories before their extraction. Add these clones to the workspace/manifest as they are created. Create the remaining portal repositories by wave from the catalog; do not auto-publish empty screens as available products.

## Required Initial Repository Files

Use the matching [template](09-repository-templates.md). Include README, applicable license/notice files, `.gitignore`, `.editorconfig`, CODEOWNERS, PR template, build manifest, locked dependencies, tests and CI. Do not copy the entire old `.github` folder indiscriminately: its root paths and workflow dependencies assume the original repository.

Example CODEOWNERS policy for `AvyukthiAI`, using proposed team names. Create/verify those teams and their repository access before enabling this policy:

```text
* @AvyukthiAI/suite-maintainers
/.github/ @AvyukthiAI/security-reviewers
/LICENSE @AvyukthiAI/release-managers
/THIRD_PARTY_NOTICES.md @AvyukthiAI/release-managers
```

Ownership entries on a later matching line replace earlier matching ownership for that path. List all required owners on the applicable line when several owners should be requested. Configure review requirements separately; an owner entry alone cannot guarantee several distinct approvals.

## Bootstrap Is Done When

The confirmed organization owns each created repository; all are private; the intended users can clone them; an unauthorized identity cannot; review/check policies behave as intended; package consumers have only required access; no secrets or inappropriate license templates were introduced. Record actual repository URLs and policy verification in the bootstrap evidence manifest.
