- CI/CD definitions and recent run logs.
- Test suites and test results (unit, integration, e2e).
- Runtime manifests and infra (Dockerfiles, k8s, terraform, helm).
- Build artifacts, deployment logs, monitoring exports (if available).
- API contracts (OpenAPI/Swagger), DB schemas, diagrams.

**Assumptions to auto-record if missing:**
- Default runtime environment (OS, Python version, container runtime).
- Default branch and commit hash used for audit.
- Any missing input must be recorded as a gap with reproduction steps.

### 4. Methodology — Stepwise, Automatable, Evidence‑First
Each step must produce artifacts under `audit-output/` and raw evidence under `audit-output/evidence/`. Scripts go under `audit-scripts/`. All scripts must accept CLI args and return deterministic outputs.

#### 4.1 Inventory & Requirements Parsing
- **Task:** Parse every `.md` into structured records with fields: `id`, `title`, `type`, `priority`, `owner`, `acceptance_criteria`, `related_files`, `line_range`, `raw_text`.
- **Outputs:** `requirements_index.json`, `requirements_index.csv`.
- **Script:** `audit-scripts/parse_md_requirements.py --root . --out audit-output/requirements_index.json`
- **Evidence:** parsing logs, sample mapping CSV.

#### 4.2 Traceability Mapping
- **Task:** For each requirement, locate code, tests, infra, and docs using static search, AST parsing, and heuristics (function/class names, API paths, OpenAPI refs).
- **Outputs:** `traceability_matrix.csv` with columns: `requirement_id`, `code_paths`, `test_paths`, `infra_paths`, `evidence_type`, `confidence_score`, `git_commit`.
- **Script:** `audit-scripts/generate_traceability.py --repo-root . --requirements audit-output/requirements_index.json --out audit-output/traceability_matrix.csv`
- **Evidence:** search commands, scripts, and CSV.

#### 4.3 Behavioral Verification (Tests)
- **Task:** Run unit/integration/e2e tests; map passing/failing tests to requirements. For missing tests, generate **test stubs** and test plans (machine‑readable).
- **Outputs:** `test_results/`, `missing_tests.json`, `test_stubs/`.
- **Script:** `audit-scripts/run_tests_and_map.py --repo-root . --requirements audit-output/requirements_index.json --out audit-output/test_results/`
- **Evidence:** test logs, junit xml, mapping to requirements.

#### 4.4 Static & Dynamic Analysis
- **Task:** Run linters, SAST, dependency vulnerability scanners, license scanners, and secrets scanners. If a test deployment is available, run DAST and safe load tests.
- **Outputs:** `security_scan/`, `vuln_report.json`, `license_report.csv`.
- **Script:** `audit-scripts/run_static_analysis.sh` (idempotent).
- **Evidence:** tool outputs, CVE lists, remediation suggestions.

#### 4.5 Architecture & Non‑Functional Review
- **Task:** Validate architecture diagrams vs code/infra; check scalability, resilience, observability, backup/recovery, performance budgets.
- **Outputs:** `architecture_review.md`, `load_test_results/`.
- **Evidence:** diagrams, smoke/load test scripts and results.

#### 4.6 Security, Privacy & Threat Modeling
- **Task:** Threat model data flows, trust boundaries; verify authn/authz, session management, encryption, secrets management, key rotation.
- **Outputs:** `threat_model.drawio` or `threat_model.json`, `security_checklist.md`.
- **Evidence:** SAST/DAST outputs, threat model artifacts.

#### 4.7 AI / LLM Governance Review
- **Task:** Inventory all LLM/model usage; verify data flows, redaction, model versioning, prompt management, output validation, and human-in-the-loop controls.
- **Outputs:** `ai_inventory.json`, `ai_governance.md`.
- **Evidence:** code references, config files, redaction logs.

#### 4.8 Compliance & Licensing
- **Task:** Verify third-party licenses, export controls, and regulatory requirements.
- **Outputs:** `license_report.csv`, `compliance_gaps.md`.

#### 4.9 Risk Assessment & Prioritization
- **Task:** For each gap assign `severity`, `impact`, `likelihood`, `priority`, `remediation_complexity`, `estimate_hours`.
- **Outputs:** `audit_tasks.json` (task list with owners, estimates, acceptance criteria).
- **Evidence:** risk scoring rationale.

#### 4.10 Remediation Plan & Tracker
- **Task:** Create prioritized remediation tasks with owners, estimates, acceptance criteria, and CI checks. Generate `tracker.html` with importable `evidence.json` and `audit-memory.json` integration.
- **Outputs:** `audit-output/tracker.html`, `audit-output/audit_tasks.json`.
- **Script:** `audit-scripts/generate_tracker.py --tasks audit-output/audit_tasks.json --traceability audit-output/traceability_matrix.csv --evidence-json audit-output/evidence/evidence.json --audit-memory audit-output/audit-memory.json --out audit-output/tracker.html`

### 5. Tracker HTML — Requirements and Behavior (enhanced)
**Core features:**
- Columns: **ID**, **Title**, **Type**, **Severity**, **Status**, **Owner**, **Estimate Hours**, **Acceptance Criteria**, **Code Link**, **Test Link**, **CI Link**, **Evidence Summary**, **Comments**.
- **Evidence Import:** UI control to upload/import `evidence.json`. When imported:
  - The tracker must match `evidence.json` entries to `requirement_id` and update `Status` automatically (Implemented / Partially Implemented / Not Implemented / Ambiguous).
  - For each requirement, show a list of evidence items (type, link, git commit, reproduction command).
  - If multiple evidence items exist, compute and display an aggregated **confidence score**.
- **Audit‑memory integration:** Option to load `audit-memory.json` to pre-populate owner assignments, previous statuses, and context notes.
- **Filters & Exports:** sorting, filtering by severity/type/status, search, CSV export, and PDF snapshot export (client-side).
- **Deep links:** direct links to code lines (GitHub/Bitbucket anchors) and CI run IDs.
- **Security:** tracker runs client-side only; no secrets uploaded. Evidence import must validate and reject entries that contain PII or secrets (use `redact_sensitive.py` server-side or client-side check).
- **Accessibility:** keyboard navigation, ARIA labels, responsive layout.

**`evidence.json` schema (recommended):**
```json
{
  "git_commit": "abcdef1234567890",
  "generated_at": "2026-10-19T21:00:00Z",
  "evidence_items": [
    {
      "requirement_id": "REQ-FUNC-0001",
      "evidence_id": "evi-0001",
      "type": "code_link|test_run|ci_log|screenshot|artifact",
      "summary": "Unit test passing for endpoint X",
      "link": "https://github.com/org/repo/blob/commit/path#L10-L50",
      "repro_command": "pytest tests/test_x.py::test_endpoint_x -q",
      "confidence": 0.95,
      "notes": "Sanitized logs; no PII"
    }
  ]
}
```

**Tracker import behavior:**
- On import, the tracker validates schema, checks `git_commit` matches the repo state (or flags mismatch), and updates rows.
- Provide an **audit trail** of imports (who imported, when, and what changed).
- Provide a **manual override** for status with required justification and evidence link.

### 6. Audit‑Memory File (audit-memory.json) — Purpose & Schema
**Purpose:** Persist audit context to enable minimal re-audit of prior work and to allow multiple LLMs/agents to continue work where previous agents left off.

**Key uses:**
- Store requirement statuses, owners, evidence pointers, previous remediation attempts, and agent/LLM prompts used (redacted).
- Provide a changelog of audit actions and sign-offs.

**Recommended schema:**
```json
{
  "repo": "git@github.com:org/repo.git",
  "commit": "abcdef1234567890",
  "last_audit_date": "2026-10-19T21:00:00Z",
  "requirements": {
    "REQ-FUNC-0001": {
      "status": "Partially Implemented",
      "owners": ["alice@example.com"],
      "evidence_ids": ["evi-0001","evi-0002"],
      "notes": "Unit tests added; integration test failing on CI",
      "last_updated": "2026-10-19T20:30:00Z"
    }
  },
  "agents": [
    {
      "agent_id": "agent-llm-01",
      "role": "traceability",
      "prompt_hash": "sha256:...",
      "redacted_input_ref": "redaction-0001",
      "output_ref": "artifact-0001",
      "timestamp": "2026-10-19T20:00:00Z"
    }
  ],
  "import_history": [
    {
      "file": "evidence.json",
      "imported_by": "alice",
      "timestamp": "2026-10-19T21:05:00Z",
      "git_commit": "abcdef1234567890"
    }
  ]
}
```

**Rules:**
- `audit-memory.json` must never contain secrets or PII. If any PII is needed for owner contact, store only hashed identifiers and a separate secure contact mapping outside the audit repo.
- Agents reading `audit-memory.json` must validate schema and record their actions back into the file.

### 8. `audit_gaps_requirements.md` — Required Structure (strict)
- **Header:** project name, repo URL, commit hash, audit date, auditors (roles + names).
- **Executive Summary:** 3–5 bullets: core objective, health score, top 5 risks, remediation summary.
- **Core Objective:** one-paragraph derived from `.md` files.
- **Traceability Summary:** counts of implemented/partial/missing/ambiguous.
- **Detailed Findings:** for each requirement:
  - **Requirement ID**  
  - **Requirement Text** (verbatim)  
  - **Type**  
  - **Implementation Status**  
  - **Evidence**: code path(s); test path(s); CI job name and run id; log snippet; reproduction command; exact git commit.  
  - **Gap Description**  
  - **Severity**  
  - **Remediation Recommendation** (step-by-step)  
  - **Estimated Effort** (hours)  
  - **Acceptance Criteria** (explicit tests/commands)
- **Appendices:** traceability matrix, scripts, raw evidence links, redaction logs, LLM usage logs (model name, version, prompt hash, redacted input ref, output ref).

---

### 9. Evidence Rules, LLM Controls, and Acceptance Criteria (explicit)
**Evidence rules:**
- Every factual claim must include **one reproducible evidence item** (code link + line numbers, test run command + output, CI job + run id, or script).
- Include exact git commit hash for audited state.
- If evidence requires credentials or production data, mark as **Not Reproducible** and provide sanitized reproduction steps.

**LLM usage & governance:**
- Allowed: boilerplate code, remediation tasks, summaries — only with redacted inputs.
- Prohibited: sending secrets, PII, or raw production data to external LLMs.
- For every LLM call record: model name, version, prompt (redacted), redacted input ref, output ref, and human verifier identity.

**Acceptance criteria for sign-off:**
- **Completeness:** every requirement has a status.
- **Traceability:** each requirement has at least one code/test/infra reference or documented reason for absence.
- **Security:** no Critical severity gaps remain open.
- **Reproducibility:** all evidence reproducible via scripts and commands.
- **Sign-off:** Audit Lead, Security Specialist, and Product Owner sign `audit_gaps_requirements.md` with date and commit hash.
