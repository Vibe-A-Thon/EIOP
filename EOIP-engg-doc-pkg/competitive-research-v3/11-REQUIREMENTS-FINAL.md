## 0. Priority formula and tier definitions (Master Prompt §13, inherited)

`PriorityScore = 0.25·CustomerValue + 0.20·StrategicFit + 0.15·RiskReduction + 0.15·EvidenceStrength + 0.10·ReuseLeverage + 0.10·Feasibility + 0.05·Differentiation − ComplexityPenalty`

Every requirement below carries the priority already assigned to its source gap in `07-GAP-REGISTER.md` — P0 is **forced** for correctness, source lineage, idempotency, permission and tenant protection regardless of score (including licensing/supply-chain, per Master Prompt §17); P1 requires score ≥ 3.15 or a documented coordinator override; P2 ≥ 2.5; everything else is P3/Research. This document does not re-run the formula or move any requirement between tiers. Three GAP-ID score overrides (GAP-13, GAP-04, GAP-26, all P1 despite a raw score below the normal P1 cut) are carried forward unchanged from the register.

- **P0** — correctness, source lineage, idempotency, permission and tenant protection, a repeatable vertical slice, reliability, core query contracts. Release phase: **Phase 0 (foundation/correctness)**.
- **P1** — high-value enterprise integration, graph evolution, ontology governance, explainable retrieval and NL query, important UX, multi-backend parity for core features. Release phase: **Phase 1**.
- **P2** — advanced reasoning, ML, federation, predictive analytics, collaborative editing, scale-out validated by demand. Release phase: **Phase 2**.
- **P3 / Research** — experimental architectures with unproven payoff. Release phase: **Research track** (not phase-gated).

REQ-ID format: `REQ-<AREA>-NN`. Areas used: **SEC** (security/ACL/injection/PII/audit/egress), **TEN** (tenant isolation), **GOV** (epistemic planes, ontology/SHACL/OWL governance, constraints, bitemporal, lineage, rules, wisdom), **OPS** (CI/licensing, SBOM, backup, air-gap, sizing, eval harness, model-runtime hygiene), **QRY** (query IR/compiler, vector/full-text, NL-query, path modes, virtualization, GraphRAG benchmarking), **ING** (connectors, identity/ER, code graph, evidence spans, digital-thread journeys), **MEM** (agent memory), **ML** (model/algorithm ports), **STOR** (backend adapters, bulk load), **STD** (SPARQL/RML standards interop), **VIZ** (visualisation UX).

**Split-gap rule applied:** a gap is split into more than one requirement only where it has genuinely separable deliverables (owning-module boundary, independent test, independent release risk) — e.g. GAP-02's write-path ACL tagging vs. read-path enforcement, as instructed by the brief; GAP-09's auth-model change vs. tool-level ACL annotations; GAP-17's branch persistence vs. governance-PR mounting; GAP-13's deterministic-ID extension vs. probabilistic-ER integration; GAP-26's connector breadth vs. permission-sync verification; GAP-10's PII recognisers vs. secret scanning; GAP-33's PPR-retriever benchmark vs. ACL-scoped community summaries. Three requirements (REQ-SEC-07, REQ-ML-01, REQ-ING-08, REQ-OPS-08) derive from undisputed STR-ID adoptions in the §1 shortlist that go beyond what their linked gap's base fix already requires (STR-rebac-01 exceed-grade consistency tokens; STR-llcpp-01 CPU-only model alternative; STR-amazon-neptune-03 Streams-based freshness; STR-ldbc-01 parity workload generator) — each still traces to a GAP-ID through its `Dependencies` column, per the rule that nothing is invented without a gap, strength or inversion behind it.

### 1.1 P0 requirement expansions (full field set)

**REQ-OPS-01 — CI licence allow-list gate.** *Data contracts:* a new `LicensePolicy` record (allow-list entries keyed by SPDX identifier, sourced from `02-TECHNOLOGY-REGISTRY.md` §3) and a legal-review queue entry schema. *API/UI surface:* none customer-facing; a CI job annotation and a build-failure message naming the offending dependency and its licence. *Threat considerations:* a dependency bump that silently introduces AGPL/SSPL/BUSL/ELv2 code would compromise the OEM/white-label offering (CAP-52) for every downstream partner; the allow-list is the only automated backstop between a `pip`/`npm` bump and a shipped legal liability. *Observability:* every CI run emits a licence-scan report artifact; blocked builds are logged with the dependency name, version and detected licence for the legal-review queue.

**REQ-SEC-01 — AEAD egress vault.** *Data contracts:* the vault's on-disk token format changes from an XOR-keystream blob to an AEAD ciphertext (nonce + tag + ciphertext); existing tokenised values need a one-time re-tokenisation pass, tracked as a migration note, not silently dropped. *API/UI surface:* none — `egress/vault.py` is an internal library used by `egress/gateway.py`; no route changes. *Threat considerations:* the XOR cipher is malleable and trivially broken under keystream reuse; an attacker who can observe two tokenised values with a repeated or partially known keystream recovers plaintext — this is a real liability for any customer PII/secret passed through the egress gateway today. *Observability:* a cryptographic-review checklist and a known-plaintext-recovery test (BM-18) must fail against the new cipher before this requirement is considered met; key-rotation events are audit-logged.

**REQ-OPS-02 — Harden local model runtime.** *Data contracts:* none new; the Ollama container's version pin and run-as-user in `deploy/docker-compose.yml` change. *API/UI surface:* an authenticating reverse proxy sits in front of the model port; no change to the `ModelPort`/`ModelAdapter` interface itself. *Threat considerations:* a root, unauthenticated, year-stale container with a documented path-traversal CVE is reachable by anything on the same Docker network — this is the lowest-effort fix with the highest immediate risk reduction in the P0 set. *Observability:* a CVE/vulnerability scan of the pinned image runs on every release and must show zero known-exploitable CVEs; proxy auth failures are logged.

**REQ-SEC-02 — MCP OAuth 2.1 resource-server auth.** *Data contracts:* MCP requests carry a per-user/agent OAuth token instead of the shared bootstrap token; `contracts/tool.py ToolRequest.actor_id`/`tenant_id` (already present) become populated from the verified token rather than left as caller-supplied strings. *API/UI surface:* `apps/mcp/main.py`'s `Authorization: Bearer` handling changes from `hmac.compare_digest` against one static secret to token-exchange/introspection against the existing RBAC/ABAC identity provider (`authn/sso.py`). *Threat considerations:* the confused-deputy pattern (C09-mcp INV-mcp-02) — every MCP action today is attributable only to the API's bootstrap token, not to the real human or agent behind it, which defeats per-user ACL enforcement (REQ-SEC-05) for the entire MCP surface. *Observability:* every tool call is logged with its resolved principal, not just "mcp-bootstrap"; failed token exchanges are rate-limited and alerted.

**REQ-SEC-03 — MCP tool ACL annotations and signed manifests.** *Data contracts:* `contracts/tool.py ToolContract` gains a required ACL-scope field alongside its existing `read_only`/`risk_level`; tool manifests are canonicalised (RFC 8785, already used by `warrant.py`) and hash-signed. *API/UI surface:* MCP tool-listing responses include the annotation and manifest digest so a client can detect a modified description before invoking it. *Threat considerations:* MCP tool-poisoning / rug-pull (C09-mcp INV-mcp-01) — a model-visible tool description is untrusted input; an unsigned, unannotated tool can silently escalate from read to write or exfiltrate data through a plausible-looking description change. *Observability:* manifest-digest mismatches are logged and the tool call is denied, not merely warned.

**REQ-GOV-01 — Storage-level epistemic-state enforcement.** *Data contracts:* extends `contracts/canonical.py KnowledgeState` (ASSERTED/INFERRED/PROPOSED/REJECTED/HISTORICAL) from an application-level enum into a mandatory, backend-persisted property checked by `validation/gate.py`; promotion events are recorded through `provenance/warrant_composition.py`. *API/UI surface:* the mutation API rejects any write lacking `epistemic_state` with a typed `ConstraintViolationError` (already defined in `ai/boundary.py`) rather than a generic 500. *Threat considerations:* today the PROPOSED-until-promoted guarantee lives in `ai/boundary.py`'s own call discipline; any write path that bypasses that module can still land as an "observed" fact — this is the same failure mode as GAP-34's agent memory, just for graph facts. *Observability:* an attempted-promotion-without-review counter; BM-15 runs this as an adversarial test on every ingestion path, not just the intended one.

**REQ-OPS-03 — Unified evaluation harness with regression gates.** *Data contracts:* a `BenchmarkRun` record (BM-ID, dataset hash, hardware profile, software versions, pass/fail, timestamp) persisted for reproducibility. *API/UI surface:* a CLI/CI entry point (`qa_bench run --all`) and a release-gate hook; no customer-facing surface. *Threat considerations:* indirect — without this harness, every other P0/P1 requirement's benchmark claim (BM-01 through BM-22) is unverifiable and could silently regress between releases ("benchmark theatre" risk named in the gap register). *Observability:* the harness is itself the deliverable; its own test is "does every BM-ID in `15-VALIDATION-BENCHMARK-PLAN.md` execute and gate a release," with historical trend charts for regression detection.

**REQ-SEC-04 — Write-path ACL-principal tagging.** *Data contracts:* every fact/chunk/edge envelope gains an `acl_principals: list[str]` field (tenant-prefixed) populated from `contracts/source_event.py PermissionMetadata.principal_refs` at ingest; derived facts compute the premise-intersection ACL via `authz/pdp.py FactPremise.acl_vector` rather than inheriting a default. *API/UI surface:* the ingestion/mutation gateway (`ingestion/pipeline.py`) rejects a fact/chunk/edge mutation missing `acl_principals` once this requirement lands (mirrors REQ-GOV-01's pattern for `epistemic_state`). *Threat considerations:* without write-time tagging, read-path enforcement (REQ-SEC-05) has nothing to filter on — this requirement is the precondition for the entire ACL story, not an independent nicety. *Observability:* an ingestion-time counter of facts written without a resolvable ACL (should trend to zero); spot-audited against `PermissionMetadata.acl_hash`.

**REQ-SEC-05 — Read-path mandatory ACL enforcement.** *Data contracts:* no new schema; `authz/pdp.py can_read`'s existing `scope`/`FactPremise` types become a required parameter rather than an optional one on every retrieval call signature in `retrieval/service.py`. *API/UI surface:* `POST /api/v1/rag`, `POST /api/v1/retrieval`, `agents/governed.py`'s agent-query path, and every MCP tool that reads graph/retrieval data all gain a mandatory `scope` argument sourced from the authenticated caller, not an optional one a caller can omit. *Threat considerations:* this is the P0 of P0s — BL-18 at HEAD shows the evaluator exists but is reachable only through one optional branch that no deployed caller exercises; two employees with different permissions asking the same question get the same, unfiltered answer today. *Observability:* BM-04's two-disjoint-user corpus becomes a release gate (via REQ-OPS-03); any leaked fact, citation, cached entry, or memory item fails the build, not just the test.

**REQ-TEN-01 — Mandatory tenant context in GraphStore protocol.** *Data contracts:* the `GraphStore` protocol's method signatures (`graph/store.py:56`) gain a required tenant-context parameter; `tenancy/isolation.py IsolationPlacement` resolves it to a backend-native unit. *API/UI surface:* every adapter call without a resolved tenant raises rather than silently defaulting to a shared space — this is a breaking change to the protocol, deliberately, so that bypassing tenancy requires bypassing the protocol entirely. *Threat considerations:* zero tenant references exist today in `hugegraph.py`, `neo4j.py`, `neptune.py`, `memory.py`, `rdf_backend.py` — a POOL-model deployment with two tenants has no data-plane guarantee against cross-tenant graph reads, only an "external gate" convention. *Observability:* BM-05's adversarial cross-tenant corpus runs against data, index, cache, log and memory simultaneously; per-tenant query counters catch anomalous cross-tenant attempt rates in production.

**REQ-MEM-01 — Governed agent-memory records.** *Data contracts:* `contracts/memory.py MemoryRecord` (currently `memory_id, kind, scope, owner, source, created_at, ttl_seconds, provenance_refs, confidence, classification, deletion_policy, content` — no ACL, no tenant_id, no explicit evidence pointer beyond `provenance_refs`, no validity window) gains `acl_principals: list[str]`, `tenant_id: str`, `evidence_ref: str` and `valid_from`/`valid_to`. *API/UI surface:* memory-write tool calls route through the same propose-not-write gateway as REQ-GOV-01; memory-read calls carry the caller's policy epoch (REQ-SEC-07). *Threat considerations:* every researched agent-memory competitor (Cognee, Mem0, Graphiti-Zep, Letta) shows the same structural absence — an agent that "remembers" a fact learned under one user's permissions must not surface it to a different, lower-privileged user, and must forget it immediately on revocation, not eventually. *Observability:* BM-04/BM-05 extended to memory; a revoked-user memory-access counter that must read zero post-revocation.

**REQ-SEC-06 — Parameterised queries and classifier-layer defence.** *Data contracts:* no new schema; the two named adapter call sites change from string-interpolated Gremlin/Groovy to parameterised calls. *API/UI surface:* none customer-visible; internal adapter code only. *Threat considerations:* property keys and labels are currently spliced into Gremlin/Groovy scripts as strings in `adapters/janusgraph.py:192,276` and `graph/hugegraph.py:525-551` — this is a provable injection surface if key/label provenance is ever attacker-influenced (not yet traced, per the gap register's own uncertainty note), and the agent firewall's regex-only defence is not a substitute. *Observability:* BM-18's injection corpus (malicious property keys/labels) runs on every release; a classifier-layer block/allow decision is logged alongside the regex firewall's decision for drift detection.

**REQ-STOR-01 — Fix named adapter defects and gate with live conformance.** *Data contracts:* no schema change; the JanusGraph key-prefix convention becomes consistent between read and write paths, Neptune requests gain SigV4-signed headers, and HugeGraph's Gremlin submissions drop the Groovy-closure dependency. *API/UI surface:* none customer-visible; adapter internals only. *Threat considerations:* silent data corruption risk — the JanusGraph mismatch can make non-canonical-ID lookups silently fail, and Neptune's LIMIT-before-filter ordering silently truncates results before label filtering, both without raising an error the caller would notice. *Observability:* BM-01 runs the identical workload against live HugeGraph, Neo4j, Neptune and JanusGraph containers in CI; any backend's results diverging outside documented semantic differences blocks the release.

**REQ-SEC-07 — Policy-epoch consistency tokens.** *Data contracts:* `authz/pdp.py PolicyEpochRegistry` (already tracks a monotonically increasing tenant epoch) and `contracts/canonical.py TrustedScope.policy_epoch` (already present) are wired into every cache key, search-index entry and memory read, not just the PDP's own `can_read` check. *API/UI surface:* retrieval-cache and tenant-index lookups gain an epoch-staleness check before returning a cached result. *Threat considerations:* without this, a permission revocation can leave stale cached or indexed results reachable until the next full re-index — exactly the gap Zanzibar/SpiceDB's `ZedToken` pattern closes, and exceeding it (per the strength-adoption register's "Exceed" rating) means EOIP's revocation story is benchmarked, not just claimed. *Observability:* BM-04's revocation-specific cases (revoke-then-query) are a named release gate; epoch-staleness rejections are counted and alertable.
