## 2. Problem, workloads, workflows
Predict future properties of entities (churn, position, item recommendation, attribute autocomplete) directly from a relational database without manual joins. EOIP workflow: operational facts in tenant stores (tickets, orders, deployments) feed entity-level predictions into the isolated prediction plane (J8); RelBench-style temporal cutoffs supply the leakage-safe split pattern for hypothesis 12.

## 4. Architecture
```
Hugging Face hub (parquet tables) -> Database (tables, pkey/fkey, time col)
   -> Task (SQL-defined labels; train/val/test tables at timestamps)
   -> [user model: PyG hetero GNN + PyTorch Frame encoders | GBDT on joined features]
   -> metrics / leaderboard
```

## 5. Under-the-hood reconstruction
Time is first-class: every table may carry a timestamp; each task fixes `val_timestamp` and `test_timestamp`; a label table row is (entity, timestamp, target); features are built only from rows with time <= the sample timestamp (the "time-consistent" sampling rule in the RDL recipe; implementation in PyG's temporal neighbour sampler, `time_attr`, see C11-pyg). Labels are generated by SQL over the database (DuckDB is a dependency) [CLAIM-relbench-03][CLAIM-relbench-04]. v3 serves stored parquet labels and regenerates on `regenerate=True`. Hypothesis: label generation is deterministic given the SQL.

## 6. Requirements inferred
FR: per-row timestamps; cutoffs per task; masked test targets. NFR: reproducible label generation, offline cache (v3 removes `RELBENCH_CACHE_DIR`; Hub fetch on first use needs mirroring in air-gap).

## 7. Performance and resource model
Benchmark reports are the authors' (GNN training on GPU in examples; hardware specifics not read). No CPU numbers found: NOT PUBLICLY VERIFIED. Data size is modest (about 22 million rows across v2 datasets). Failure mode: neighbourhood sampling cost on large relational joins.

## 8. Strengths
Time-aware protocol that blocks future-row leakage; standard tasks and leaderboards; Apache-2.0 code. Exceed: add calibration, drift and provenance on top.

## 9. Limitations
| Class | Item |
|---|---|
| Evidence | The headline RDL gain is from authors' own user study ("order of magnitude less human work", one data scientist) [CLAIM-relbench-05] |
| Independent | A 2026-08 paper by Prior Labs and co-authors (Leskovec among them) says RelBench's manual baseline is a reference, not a ceiling, and that flattening the database to a single table with TabPFN-3 is competitive with specialised relational models. It is a vendor-authored preprint and is not peer reviewed [CLAIM-relbench-06] |
| Operational | v3 breaking changes; hosted-data terms unclear; label regeneration changed (e.g. `rel-event/user-repeat` train labels 3,842 to 2,972 rows) [CLAIM-relbench-03] |
| Fit | benchmarks are academic; no multi-tenant, ACL or ontology concept |

## 10. Deployment, licensing, operations
Code is Apache-2.0 and CPU-capable in the loader; GNN examples need PyG (sampling via `pyg-lib`, wheel by torch/CUDA build). Air-gap: viable if the Hub datasets are mirrored locally. Legal trigger: dataset licences, especially third-party ones. No nvidia package in the declared base dependencies [CLAIM-relbench-04].

## 11. Delta versus baseline
BL-44/BL-57 lack any leakage-safe evaluation harness. RelBench contributes the protocol (cutoffs, masked targets) and a ready GBDT-vs-GNN comparison method, not a runtime component. Directly supports CAP-78.

## 13. Per-capability decisions
CAP-78: REUSE protocol (not code). CAP-64: EXPERIMENT (entity-level prediction on tenant stores). CAP-65: BUILD cutoff-based temporal split. CAP-43: BUILD prediction plane.

## 14. Tests
Reproduce one classification task on CPU with a GBDT baseline; add a leakage canary (feature from after cutoff) and require failure; mirror Hub data offline; confirm label tables identical across two runs.

## 15. Risks
API churn; dataset terms; academic datasets unlike enterprise data; GPU-trained published numbers non-binding under H-17.
