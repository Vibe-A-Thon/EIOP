## 1. Identity, current status, tier, sources

Agent2Agent (A2A) is an open protocol for discovery and task-level collaboration between independently built agents (repo `a2aproject/A2A`, spec at a2a-protocol.org). Licence **Apache-2.0**; described as "an open source project under the Linux Foundation, contributed by Google" [CLAIM-a2a-01]. Governance: a Technical Steering Committee with nine company-held seats (Google, Microsoft, Cisco, AWS, Salesforce, ServiceNow, SAP, IBM, Bloomberg) in a "Startup Phase", one vote per member, steady-state composition to be decided later [CLAIM-a2a-02]. The GOVERNANCE file does not itself name a Linux Foundation project; LF hosting rests on the README sentence only (confidence 0.7). Latest release page: v1.0.1, 2026-05-28 [CLAIM-a2a-03]. Python SDK `a2a-sdk` 1.2.3, Apache-2.0 [CLAIM-a2a-04]. Status: active, early-production (1.0 reached; adoption depth UNVERIFIED). Cross-reference: MCP (tool/context protocol) is covered in `C09-mcp.md`; this file covers only the agent-to-agent layer.

## 2. Problem, workloads, workflows

Problem: agents from different vendors/frameworks cannot discover each other or delegate long-running work. Core objects: Agent Card (capabilities, endpoint, auth schemes), Task (long-running, with lifecycle), messages with text/file/structured-JSON parts; transports JSON-RPC 2.0 over HTTP(S), SSE streaming, asynchronous push notifications [CLAIM-a2a-01]. EOIP workflow: a customer's external procurement agent (any framework) discovers the EOIP "knowledge agent" Agent Card, submits a task "assess supplier risk", EOIP runs a governed retrieval plan and returns a cited artifact, with the caller's identity mapped to an EOIP principal.

## 4. Architecture

```
 caller agent --(1) GET Agent Card--> /.well-known/... (location UNVERIFIED)
 caller agent --(2) JSON-RPC 2.0 over HTTPS--> A2A server --> agent executor --> (tools via MCP)
        ^---------- SSE stream / push-notification webhook (task updates) ----------|
 control plane: auth scheme declared in card; data plane: messages/artifacts
```

## 5. Under-the-hood reconstruction

Stateless HTTP request/response envelope (JSON-RPC 2.0) with a server-side task store keyed by task id; the server decides durability (hypothesis: SDK ships an in-memory store and a pluggable interface; not verified). Streaming via SSE; asynchronous completion via webhook to a client-supplied URL, which creates an SSRF surface the receiving side must constrain (reasoned inference). No graph, storage or reasoning concerns. Security: authentication is declared per card, transport-level; fine-grained authorisation, tenancy and audit are left to implementers (reasoned inference from the README's own "formalize authorization" note).

## 6. Requirements inferred

FR: publish an Agent Card per EOIP tenant/agent; accept tasks mapped to `QueryPlan`/agent runs (BL-08, BL-48); stream progress; return artifacts with evidence spans. NFR: every inbound task authenticated and mapped to a tenant principal (BL-19/20); outbound webhooks go through the egress gateway (BL-45); idempotent task submission; per-tenant rate limits.

## 7. Performance and resource model

No benchmarks found; protocol overhead is HTTP/JSON. Failure modes: long-lived SSE connections behind proxies, webhook delivery loss (needs retry/DLQ analogous to BL-24), task-store loss on restart. No numbers given.

## 8. Strengths

Broad multi-vendor TSC and Apache-2.0 licence reduce lock-in; complements MCP (agent-to-tool vs agent-to-agent). Match: expose an A2A façade over the existing MCP/agent runtime. Exceed: authorisation that enforces source ACLs end-to-end, which A2A itself does not specify.

## 9. Limitations

Algorithmic dead-ends: none (it is a wire protocol). Operational: webhooks need inbound reachability, awkward in air-gapped single-node deployments. Developer friction: spec surface still moving (1.0 only since 2026; earlier-version churn not verified). Governance risk: company-seat TSC dominated by hyperscalers; steady-state governance undecided [CLAIM-a2a-02]. Prompt-injection across agents is not solved by the protocol (reasoned inference).

## 10. Deployment, licensing, operational viability

Apache-2.0 spec and SDK: redistribution-safe (patent grant included). Pure HTTP, no cloud dependency, so air-gap viable between in-perimeter agents. One-node friendly. Legal-review trigger: none identified beyond standard Apache-2.0 notices.

## 11. Competitive delta vs EOIP baseline

EOIP has MCP server with read-oriented tools (BL-47) and in-house agent runtime (BL-48); no A2A endpoint (absent, new). Source-ACL enforcement in retrieval is absent (BL-18), so exposing EOIP to external agents before BL-18 closes would widen a P0 leak.
