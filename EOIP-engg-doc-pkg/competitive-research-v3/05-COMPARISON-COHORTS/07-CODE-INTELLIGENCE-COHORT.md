## 1. Workload class and comparison basis

**Workloads.** Developers and agents ask "where is X defined/used," "what breaks if I change Y," "who owns this file," "what vulnerable dependency reaches this service," across one or many repositories, with answers scoped to what the asking principal may see, kept current as commits land, and joinable to Jira/incidents/SBOM for root-cause and blast-radius work (journeys J1 code search, J9 digital thread, J10 change impact).

**Why comparable.** All 16 members build or consume some notion of a code graph or code fact store, and 01-SYSTEM-BASELINE scores EOIP's own code graph (BL-42) against this exact capability set (CAP-66..69). They differ sharply in **precision tier**:
- **Compiler-grade** (type-checked, full build): CodeQL, SCIP (scip-java/clang/typescript), Joern (per-frontend), Sourcegraph precise indexes (consumes SCIP).
- **Syntactic** (parse-tree, no type resolution): Tree-sitter, Stack Graphs (name resolution without a build), OpenRewrite LSTs (compiler-grade for Java only, syntactic-ish for others), Graphify/CodeGraph (heuristic).
- **Text/pattern**: Semgrep (syntax-tree pattern match, not full semantic), Sourcegraph Zoekt (trigram), Greptile (chunk + embedding, no graph DB named), grepai (Tier C, semantic search only).
- **Metadata/catalog, not code graph at all**: Backstage (ownership catalog), Dependency-Track (SBOM/vuln graph), CAST Imaging (architecture reverse-engineering, proprietary), SonarQube (Tier C, quality findings).

Comparing a CodeQL-grade engine to Zoekt on "precision" would be a category error; this cohort keeps the tiers explicit in every table.

**Excluded.** Visualization of code graphs (cohort 08); generic ontology/RDF tooling (cohort 15); pure LLM agent frameworks with no code-specific graph (C09, separate cohort). Glean (glean.com, enterprise work-graph) is a different product from Glean (Meta, code intelligence); only the Meta one is in this cohort (`C15-glean-meta.md`; the placeholder `C15-glean-code-intelligence.md` has no CLAIM records and is excluded per brief rule).

## 4. Performance evidence

No member in this cohort has a reproducible, independently measured benchmark; every deep dive states this explicitly:
- Sourcegraph: "No vendor benchmark was retrieved; NOT PUBLICLY VERIFIED" (section 7).
- Tree-sitter: "No benchmark retrieved; NOT PUBLICLY VERIFIED" (section 7).
- SCIP/LSIF: "No benchmark retrieved: NOT PUBLICLY VERIFIED"; the only numeric figures are resource statements for `scip-clang` (about 2 MB temp space per translation unit, ~2 GB RAM per core) [CLAIM-scip-lsif-09] — a resource footprint, not a throughput benchmark.
- CodeQL: "No independent benchmark retrieved: NOT PUBLICLY VERIFIED."
- Joern: "No benchmark retrieved: NOT PUBLICLY VERIFIED."
- OpenRewrite: "throughput NOT PUBLICLY VERIFIED"; sizing is vendor-stated only.
- Dependency-Track: vendor claims only, ">20,000 SBOMs/hour, >250,000 SBOMs per instance," hardware and SBOM size unstated [CLAIM-dt-02] — labelled a vendor claim, not independent evidence.
- Backstage: "No benchmarks found."

**No winner can be declared on speed, index size or scale from this cohort's evidence.** The one qualitative, falsifiable ordering supported by the evidence is precision-tier cost: compiler-grade indexers (CodeQL, SCIP/scip-java/clang/typescript) require a full build and are "typically far above Tree-sitter parse cost" (reasoned inference in the SCIP deep dive, not measured), while Tree-sitter's incremental reparse is "proportional to the edited region," a design intent, not a measured result.

## 5. Findings

1. **Precision tiers are not interchangeable, and no member spans all three.** Compiler-grade engines (CodeQL, SCIP indexers, Joern) require a successful build; syntactic engines (Tree-sitter, Stack Graphs) do not but cannot resolve types; text engines (Zoekt, Semgrep patterns) need neither but answer narrower questions. EOIP's own BL-42 (Tree-sitter-class, 2 languages) sits in the syntactic tier only; SCIP/LSIF absent (01-SYSTEM-BASELINE).
2. **The two most "precise" engines (Sourcegraph, CodeQL) are also the two with the hardest licence blocks.** Sourcegraph's precise indexes are enterprise-only under a proprietary relicense (2023) [CLAIM-sourcegraph-03,-04]; CodeQL's CLI forbids CI automation and non-open-source-codebase use without a paid GHAS licence [CLAIM-codeql-05]. Every corresponding deep-dive Decision is REJECT bundling / REJECT dependency.
3. **SCIP is the only compiler-grade format that is both open (Apache-2.0) and vendor-independent (community governance since the "future of SCIP" announcement)** [CLAIM-scip-lsif-01,-02]. It is the consistent INTEGRATE target across Sourcegraph, SCIP/LSIF, and Glean (Meta) deep dives' own decisions.
4. **No member provides a built-in change-impact digital thread (CAP-69) except the proprietary CAST Imaging.** Every open/permissive member (Tree-sitter, SCIP, Backstage, Dependency-Track, CodeGraph) only supplies a plugin/partial building block (diff hunks, references, ownership, SBOM edges) that EOIP must assemble; the cohort's own Decisions are consistently BUILD for CAP-69.
5. **Permission enforcement in code search/answers is weak across the entire cohort, not just at EOIP.** Sourcegraph's ACL is repo-level only [CLAIM-sourcegraph-09]; SCIP has none [Appendix B]; Augment and Greptile are unknown/unverified. EOIP's own BL-18 gap (enforcement exists but no deployed caller passes `scope`, 01a) is therefore a gap shared industry-wide, not a unique EOIP weakness, though it remains EOIP's P0.
6. **Two members are effectively unusable as dependencies for reasons other than price: one is dead, one is legally blocked by copyleft.** Stack Graphs is archived with no maintained fork [CLAIM-stack-graphs-01,-03]; srcML (Tier C) is GPL-3.0, which conflicts with the project's hard GPL/AGPL constraint (user memory: "GPL/AGPL is a hard constraint") [CLAIM-srcml-01].
7. **The "graph" claim in several AI-native tools is not evidenced as a graph database.** Greptile's docs describe PostgreSQL+pgvector with chunker/summarizer workers, "no graph database named," despite marketing saying it "constructs a graph index" [CLAIM-greptile-01,-03]. GitNexus and CodeGraph claim embedded graph databases (LadybugDB, unnamed) that were not independently verified beyond their own READMEs.
8. **MCP tool exposure is now common** (Augment, CodeGraph, CAST Imaging, Graphify all expose MCP servers/tools), consistent with EOIP's own BL-47, but none of the reviewed MCP surfaces (including EOIP's own, per 01a) is shown to propagate per-user identity or tenant through the MCP layer.
9. **Dependency-Track v5 ("Hyades") removed the message-broker dependency and all non-PostgreSQL databases**, simplifying its one-node story relative to v4 [CLAIM-dt-02] — a useful design precedent for EOIP's own SQLite-first posture (BL-24/`DurableJobStore`, cohort 16).
10. **CI integration is asserted, not demonstrated, almost everywhere.** No deep dive in this cohort ran a member inside a CI pipeline and measured wall-clock cost; CodeQL's own licence explicitly restricts CI/CD automation outside GitHub-hosted OSS repos [CLAIM-codeql-05], which is itself evidence that "CI-friendly" claims need a licence check, not just a technical check.
